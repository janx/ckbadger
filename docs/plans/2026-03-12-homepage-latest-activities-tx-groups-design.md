# Homepage Latest Activities Tx Groups Design

## Goal

- Redesign the homepage `Latest Activities` card so it groups items by transaction and uses the card space more efficiently while staying faithful to the existing owner-activity model.

## Principle Alignment

- CKB Native: keep transaction as the homepage-level unit while preserving owner-level activities as the interpreted on-chain action units shown inside each group.
- Local First: avoid schema or API changes for the first iteration; derive grouped presentation entirely in the frontend from the existing latest-activities feed.
- Agent Friendly: keep the design explicit, rule-based, and testable through pure grouping and summary helpers.

## Context

- The current card in `frontend/components/latest-activities.tsx` renders each `GlobalActivity` row independently.
- The latest feed API in `crates/api/src/routes/activities.rs` returns a flat `GlobalActivity[]`.
- This causes the same transaction metadata (`txHash`, block, timestamp) to repeat across multiple adjacent rows when one transaction touches multiple owners.

## Decision

- Use a grouped-list layout, not a ledger/matrix layout.
- Group rows by `txHash` in the frontend only.
- Render one homepage card row per transaction group.
- Default-expand the first 3 owner activities inside each group.
- Show at most 4 transaction groups on the homepage.

## Rejected Alternative

- Ledger/matrix layout was considered, with senders on the left and receivers on the right.
- It was rejected for the first iteration because many CKB transactions are multi-party and script-heavy; a matrix view would imply a stronger transfer-path interpretation than the current activity data actually guarantees.

## Data Model

- Keep using the existing `GlobalActivity` API response.
- Introduce a frontend-only view model, for example:

```ts
interface TxActivityGroup {
  txHash: string;
  blockNumber: number;
  txIndex: number;
  timestamp: string;
  participants: GlobalActivity[];
  participantCount: number;
  hiddenParticipantCount: number;
  summary: string;
}
```

- Group key: `txHash`
- Group ordering: newest first, using the first activity encountered for that transaction
- Participant ordering inside a group:
  1. negative `ckbDelta`
  2. positive `ckbDelta`
  3. zero `ckbDelta`
- Within each bucket:
  1. larger absolute `ckbDelta` first
  2. more `assetChanges` first
  3. original feed order as the stable fallback

## Summary Rules

- The summary line must be generated by explicit rules, not by speculative transaction labeling.
- Priority order:
  1. DAO events: `DAO deposit`, `DAO withdraw request`, `DAO withdraw complete`
  2. Object or identity events: examples include `Spore transfer`, `M-NFT transfer`, `.bit update`, `did:ckb transfer`
  3. Structural fallback: `X sent · Y received`
  4. If asset events exist and the fallback is used, append `· Z asset events`

- The card must not infer higher-level intent such as swap, bridge, or minting routes when the current feed does not explicitly provide that meaning.

## UI Layout

- Replace the current per-activity layout with grouped transaction blocks inside the same terminal panel shell.
- Each transaction group contains:
  - header row: `txHash`, block link, relative time
  - summary row: generated summary string
  - participant rows: up to 3 owner activities
  - overflow hint: `+N more` when additional participants exist

- Participant row content:
  - left: owner address link
  - right: `ckbDelta`
  - trailing badges: a compact subset of `assetChanges`

- Metadata that currently repeats on every activity row (`txHash`, block, time) should appear only once per group.

## Interaction

- Clicking the transaction header or hash goes to `/tx/{hash}`.
- Clicking a participant address goes to `/address/{address}`.
- The homepage does not add per-group expand/collapse in this iteration.
- The existing new-item highlight behavior should move from the individual activity row to the whole transaction group.

## Responsive Behavior

- Desktop:
  - preserve the existing terminal-panel styling
  - show grouped transaction blocks with compact spacing

- Mobile:
  - keep a single-column stack
  - show the same 3 participant rows maximum
  - limit badge count per participant if needed to avoid wrap explosions

## Scope

- Files expected to change in implementation:
  - `frontend/components/latest-activities.tsx`
  - a new pure helper module in `frontend/lib/` for grouping and summary generation
  - new frontend tests for the helper and the component

- No API change
- No store change
- No websocket protocol change
- No schema impact

## Testing

- Add pure-function tests for:
  - grouping by `txHash`
  - summary priority rules
  - participant sorting

- Add component tests for:
  - same-transaction activities rendering as one group
  - only 3 participant rows shown by default
  - `+N more` overflow hint
  - correct summary text for DAO and object/identity cases
  - group-level highlight when a new transaction appears

## Risks

- If the frontend requests too few raw activities, grouping can collapse to too few visible transaction groups.
- Summary rules can become noisy if too many badges or event types are surfaced at once.
- Input-only owners may still appear as hex fallback addresses because the current latest feed only has full lock-script details from outputs; this is acceptable for the first iteration because the redesign does not worsen the underlying data constraint.

## Result

- The homepage card becomes transaction-centric instead of row-centric.
- Repeated transaction metadata is removed.
- The card shows more meaningful on-chain structure without changing storage or API boundaries.
