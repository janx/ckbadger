## Lazy cycles extension (assigned after the bulk checkpoint)

- Gap 6/24 executes on demand only. Use the in-process CKB script verifier with the committed transaction's epoch and node consensus hardfork activation data; keep the existing exact RPC cell/header resolution and remove the debugger subprocess.
- Persist group cycles beside the existing lazy total as a domain `sync_meta` row keyed by transaction hash, atomically under the canonical write gate. No bulk fields or rows are added. Delete the row alongside the transaction mapping during rollback; the API remains read-only.
- Read contract: `get_tx_group_cycles(tx_hash)` returns each script hash, lock/type group kind, and exact cycles. The group sum must equal the lazy transaction total.

## Type ID retirement follow-up

- The initial 12M candidate failed at mainnet block **11,993,376**, transaction `0x372ba2b2122214855b4a2c34265d3e311798287169bdbd1af50afd49a11a33ab`: a valid native Type ID replaced ELF code with 31,560 zero bytes. The old invariant rejected this legal retirement. Raw failed-run evidence is retained in the scratch performance artifacts.
- Bulk and live transitions now clear only the consumed active executable binding; non-ELF state is never added as a binary version. Historical family/version/deployment metadata remains available. Later non-ELF→ELF reactivation binds the new executable, including when the historical ELF outpoint no longer exists. Burning the active code also clears its current binding.
- Live changes record chronological mapping and metadata undo. Rollup refresh consumes the canonical mapping restored by undo; the independent scan-and-repair path was removed because it could resurrect a retired non-ELF payload as code. This is domain-only; no append-only payload changes.
- Bulk writes mappings only in the final snapshot into a fresh store; label import seeds metadata but never mapping rows. No earlier snapshot can retain a retired binding. No new bulk per-cell state, scans, rows or VM work were added.
- Regression evidence: old live and bulk paths both reject retirement; the old refresh scan binds the non-ELF hash instead of leaving the reference retired. Fixed tests cover retirement, reactivation, burn, active-input matching, lock/type usage, same-batch chronological transitions, stepwise reorg, preserved deployment history, fresh final-snapshot omission, and unchanged append-only payload bytes.
- Validation: full indexer suite **1,792 passed**; final targeted checks, workspace check and strict indexer clippy are recorded with the follow-up commit. Re-sync remains **yes** for the integrated redesign.

## Family attribution after code retirement

- A post-timing read audit exposed a distinct upstream aggregation defect: family totals were the sum of current binary-version totals, so retiring a Type ID erased its still-live users and cumulative family usage. The obsolete candidate run was interrupted and retained as superseded evidence; it is not an accepted performance comparison.
- The shared `ScriptFamilyMembershipIndex` now distinguishes observed family provenance from optional current executable binding. Observed native Type ID deployments retain their unique registered family through retirement or burn; conflicting family/binary attribution fails with reference context. A retired reference is never attributed to its last binary version.
- The shared `ScriptFamilyUsage` operator aggregates each canonical reference form exactly once, validates nonnegative counters/capacities and occupied-capacity bounds, checks overflow atomically, and exposes an exact persisted-total consistency check for the read-only API. Writer family rollups use this operator rather than summing version counters. The index is built once per rollup/request; no per-transaction state, rows, schema fields, or VM execution were added.
- Only existing **domain** family rollup rows change. Live/bulk/undo tests preserve historical versions and deployment metadata, keep retired version usage at zero, retain family usage through retirement/reactivation/burn, and prove immutable append-only payload bytes remain unchanged.
- RED evidence is preserved in `type-id-family-red.log` (79 and 6 live family users incorrectly became zero) and `type-id-family-bulk-red.log` (the fresh retired snapshot lost its one live family user). GREEN covers same-batch transitions and each rollback boundary, with one reference observed under multiple versions counted only once. Two older synthetic data-hash fixtures were corrected to make their reference hash equal the binary hash, as required by the data-hash contract; the unchanged-rollup read/write budget assertions remain unchanged. Two family-total expectations were updated to the new provenance contract: known data-hash references remain family members without a current code-cell binding, and same-family ambiguous executable candidates retain one family user while both version totals stay zero.
- Validation: 15 focused helper tests, full indexer **1,792** and store **707** unit tests, workspace check, and strict store/indexer all-target clippy all passed. Raw first-failure and final-green logs are retained in the scratch performance artifacts. Re-sync remains **yes** for the integrated redesign.
